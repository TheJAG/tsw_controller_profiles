# TSW controller profiles (TheJAG)

This folder is both the live config dir of the TSW Controller App (`C:\Games\Tools\tsw-controller-app.exe`, it reloads `profiles/*.json` on change) and the git repo published at github.com/TheJAG/tsw_controller_profiles. Controller: Thrustmaster TCA Quadrant Airbus. Every released train ships with four things: a working profile in `profiles/`, a release copy in `releases/`, a docx + pdf manual in `profiles/documentation/`, and a `DONE ✅` line in `README.md`.

## Recipe for a new train

1. Ask which train, then confirm the API answers: `curl -H "DTGCommKey: <key>" http://127.0.0.1:31270/get/CurrentDrivableActor.ObjectClass` (key file: `C:\Users\m_jag\OneDrive\Documenten\My Games\TrainSimWorld7\Saved\Config\CommAPIKey.txt`). The user must sit in the cab.
2. `node tools/capture_train.js` (train stationary, master key/switch on) dumps the controls, detects cab pairs and sweeps every lever into `tools/captures/<ObjectClass>.json` (committed). Vehicle class names (`RVM_..._C`) come from the capture's `objectClass` and from `tools/pak_classes.txt` (every `RVM_*` per DLC pak; regenerate with the hyphen-aware grep from the gotchas below). Manual fallback: `dump_controls.js`, `levers.js`, `sweep_levers.js`.
3. `node tools/draft_profile.js tools/captures/<Class>.json --family <uk-unit|uk-dmu|de-unit|nl-unit> --name "Class 153" --dev dtg` writes `profiles/<game>-<train>-<dev>-thejag-<unixtime>.json` from the family template (`tools/families.json`: Class 333, Class 153, BR 440, ICMm) with the user's fixed control-to-button layout. Read the draft and its unmatched list; levers are `direct_control` only (no `sync_control` any more), buttons `momentary` with direct values, latching buttons `toggle`, wipers relative steps.
4. The user tests on the controller and reports; iterate. Then `node tools/build_release.js profiles/<file>.json`.
5. Manual (schematic format, current standard since the Class 333): `node tools/draft_manual.js profiles/<file>.json --family ... --operator ... --route ... [--logo ..] [--diagram .. --source ..]` scaffolds `tools/manual/trains/<train>.json`; fix the `_todo` items (checklists, `start` = recommended starting notch, green dot), then `node tools/manual/render_manual.js tools/manual/trains/<train>.json`. It writes the self-contained HTML and the A4 PDF straight into `profiles/documentation/` via headless Chrome. Render the PDF with `tools/pdf2png.ps1` and look at the PNG before committing. Loco pictures: prefer drawn side views from Wikimedia Commons (search the Commons API in namespace 6); logos go in `tools/assets/`; a logo that must appear in the text colour is made from its white-on-transparent version with `tools/recolor_logo.ps1` (flat navy, alpha kept, soft downscale; the old `invertToNavy` CSS filter came out black with hard edges). The older Word-template path (`tools/gen_manual.js` + `tools/specs/`) is only for touching up the pre-333 manuals.
6. README line via `node tools/readme_status.js "<README name>" <soon|done> --profile <slug> --dev DTG` (`--add "<country>"` for a new name; it also regenerates `tools/trains.json`). `SOON 🟨` while the cab test is pending, `DONE ✅` after it. Messages are in the style "Added and released X from <route>".

## Working rules (user decisions, 2026-10-10)

- Always commit and push to the repository after making changes to the code, profiles, manuals or tooling; do not wait to be asked. Use the commit message style above.
- Use Opus 5.5 subagents (`model: "opus"`) for delegable work where it makes sense (pak scans, research, drafting data files), but Fable stays the orchestrator and the reviewer: it plans, checks the subagents' results and does the final edits.
- Keep Fable's context for orchestration and review (user, 2026-10-10): the in-game work per train (menus, loading a midday service, desk photo, `capture_train.js`) goes to a subagent briefed with `tools/CAPTURE_AGENT.md`; it runs one train at a time (one game, one screen). Fable only steps in when a capture comes back with locked levers that the script cannot handle.
- Loco drawings: first look on Arthur's Treinenpagina (https://www.arthurstreinenpagina.nl/), whose author gave the user permission to use the drawings in these manuals with a reference to the site (request mail "Toestemming gebruik tekeningen", 2026-02); caption "Tekening: Arthur's Treinenpagina, arthurstreinenpagina.nl". Wikimedia Commons drawings are the second choice. Third, a web search for other sites with side-view drawings or schematics (railway drawing sites, manufacturer pages, enthusiast pages; check the licence or ask for permission as with Arthur, and credit the source in the caption). Photos are not used as the side view: only when all three find nothing (BR 440, 2026-10-10) does the manual go without a `diagram`, and the checklists and cab band spread over the free space.

## Manual conventions (decided 2026-10-09, keep them)

- Data file keys under `controls`: `speedbrake`, `leftThrottle`, `rightThrottle`, `flap` (levers: `name`, `notches` top to bottom, `start` index or `null`), `leftThrottleButton`, `rightThrottleButton`, `gearLever`, `eng1`, `eng2` (`start: true` draws the dot at the switch's OFF end), `leftAux`, `rightAux`, `roundAux`, `rudTrim`, `autoBrk` (six `positions` with `short` and `desc`, `start`), `modeSwitch` (`left`/`right` meanings), `parkBrk` (`flat`/`up` meanings). `null` = not assigned, drawn greyed.
- Green dot = recommended starting position. The AUTO BRK headlight dial's dot is always on Off (user, 2026-10-10). On a combined power/brake handle that is Max brake (just before Emergency), never 0: a parked train is always held on the brake (user, 2026-10-10). Lever notches are pills beside the slot, top to bottom, no arrows. The AUTO BRK rotary is a dial with the description under each position. The mode switch reads "slower ◀ · ▶ faster" with no "spring loaded" text. PARK BRK pivots on its right end: flat = key out, dashed upright = key in. Captions are "Left aux", "Right aux", "Round aux" with no "on-off" or "hold". The bottom-right block is the controller photo, not a table.
- New trains get HTML + PDF only; do not create docx files any more.
- Every logo in the header, operator and developer alike, is in the navy scheme (user, 2026-10-10): flat navy #223261, pale #c5cde0 for a second tone, white for marks on a navy ground. Keep the original beside it as `logo-<x>-navy.<ext>`: SVGs get their fills replaced, white-on-transparent rasters go through `tools/recolor_logo.ps1`, coloured rasters with a white mark (DTG, DB) are mixed per pixel between navy and white.
- Since the ICMm (2026-10-10): the bottom-right controller block is replaced by a full-width band with a screenshot of the driver's desk (`cab` key: `file`, `height` ≈ 196, `position`), taken in the cab view with the HUD hidden (F1), daylight, a little windscreen above the desk, cropped with `tools/crop_image.ps1` to about 3.1:1 (JPEG, ≤ 1900 px wide, in `tools/assets/<train>-cab.jpg`). The schematic shrinks a little to make room (`schematicHeight`, default 596).
- The side-view drawing at the bottom is always 48 px tall (the Class 333 drawing at full width), centred; the renderer strips a flat background around it in-page (`diagram.clean`, default true, `tolerance` 40); set `clean: false` for photos and transparent SVGs. With no drawing at all (no `diagram` key, BR 440) the checklists and the cab band spread over the free space instead; that is the fallback only when no drawing exists, not a style choice.
- Lever assignment follows the real cab: the lever the driver has on the left goes on the left TCA throttle, the right one on the right (ICMm: throttle left, brake right). An AFB / speed setter goes on the flap lever when the train has one. The speedbrake lever is always the reverser.
- The left and right aux squares are for switching the safety systems on and off (ATB / PZB / SiFa / AWS-TPWS / DVD-vigilance isolation or fuses), as `toggle`; other latching switches (train voltage, compressor, gauge lights) go on the round aux or stay out. The left throttle button is the sander when the train has one; if not, the nearest traction aid (ICMm: traction reduction) or nothing.
- The side-view drawing must show the whole consist, every unit of the set as it runs in the game (ICMm: three cars), not only the leading car.
- A lever without detents (SNG power/brake handle) gets `continuous: true` in the manual data: the slot shows a filled inner track, `notches` holds only the named points with `null` for the gaps, no ticks. In the profile it is a `direct_control` with `min`/`max` and no `steps`.
- Lever direction rule (user, 2026-10-10), check it for every lever of every train:
  1. Look in the cab where the handle sits at 0 / Off / Release and at full power / full brake / Forward (desk screenshot or the capture's notch values plus the cab view). Some trains have the brake pushed away from you, some pulled towards you; the same goes for throttles and reversers (Class 153: power is pulled towards you, 7 is nearest the driver; the brake is pushed away, Emergency furthest away).
  2. Set `invert` so the TCA lever moves the same way as the handle in the cab. Pushed away from you the TCA lever reads raw 0, pulled towards you raw 1 (all three levers). So plain = raw 0 gives game value 0 at the far end; inverted = the game's last notch is at the far end.
  3. The manual must match the cab and the profile: notch pills top to bottom = far end of the handle's travel to the end nearest the driver = TCA pushed away to pulled towards you. `draft_manual.js` derives that from the profile (plain lever: notch 0 on top; inverted: last notch on top); `--flip` only if the cab proves the profile and the pills disagree, and then fix the profile rather than the pills.
  4. The user's cab test decides; never change another train's levers or manual on the strength of one train's test.
- Every finished manual is also published as an artifact in the chat (the self-contained HTML) so the user can look at it right away.

## Gotchas learned

- Pak class names can contain hyphens (`Class377-3`, `SD40-2`), so keep `-` in the grep class. Newer paks (Medway Valley, Birmingham–Crewe, Tadami, BR 147) store names without the `.uasset` suffix and far from the end: grep the whole file for `RVM_[A-Za-z0-9_-]*` instead.
- Numeric `step_thresholds` are mirrored when `invert` is true; express them on the raw lever axis. A dead band around a notch is done with `threshold_tolerance`; a continuous zone is a `null` step with `threshold`..`threshold_end` (BR 440 and SNG combined handles: 0 at raw 0.5 with tolerance 0.07–0.08, free brake and power zones either side).
- Push buttons toggle on every value change through the mod, so a `momentary` 1-then-0 toggles twice. Use `toggle`.
- Spring switches (horn, sander, cab light, PZB buttons) rest at 0.5; send 1 or 0 while held and 0.5 on release.
- The gear lever is the safety acknowledge: AWS reset (UK), SiFa (Germany), and on Dutch stock the deadman pedal, since ATB has no acknowledge button. Setting the ICMm `DeadmanPedal` through the API moves the pedal but does not clear the warning, so Dutch stock uses the game key `Q` on the gear lever (user test, 2026-10-10).
- A combined power/brake handle (SNG `MasterController`, identifier `Throttle`) runs -1..1: Emergency -1, Max Brake -0.9, the game snaps inputs -0.06..-0.10 to min brake (-0.1, 5 %) and 0.05..0.10 to 5 % power (0.1), 0 is -0.05..0.04, beyond ±0.1 brake and power are continuous. The profile gives min brake and 5 % power their own notches beside a 0 dead band (raw 0.5 ±0.02, user-tuned) and free zones outside them. `direct_control` takes negative `min`/`steps` (Class 323 precedent). Through the API the handle once stuck at -0.1 when sent 0 straight from -0.9; `capture_train.js` ramps on restore. The sweep covers the lever's own range since 2026-10-10 (`--range` to clip). The BR 440 `MasterController` is 0..1: Emergency 0..0.04, max brake snapped 0.1, brake continuous 0.10..0.40, min brake 0.41 (0.41..0.45), 0 at 0.46..0.54, min power 0.59 (0.55..0.59), power continuous 0.60..1; one API set crosses at most one of those gates (probe in `tools/captures/RVM_NWB_DB_BR440_0_C_handle_probe.txt`). Both handles use the same lever geometry: max brake at raw 1 ±0.04, free brake zone to 0.58, min brake 0.55 ±0.03, 0 at 0.5 ±0.02, min power 0.45 ±0.03, free power zone from 0.42, full at 0 ±0.04.
- Notch beeps / "lever wobbles" on a stepped handle (Class 171, 2026-10-10, fixed): the app raises a change event on every axis reading and re-sends the step value each time (no "unchanged, skip" check; inside a band it sends the same value, in a gap nothing), and the mod re-applies it to the lever. A re-send is only silent when the value is exactly what the game stores. Two things made it audible: (1) the game snaps a lever set through the mod to its own notch positions (171 power notches are k/14), and a step value a hair *below* such a position re-snaps with a click on every re-send (P1, P4, P5 were below, P2, P3, P6 above and silent): read the lever's `InputValue` after the TCA has set it (`node tools/probe_lever.js <Lever>` shows stored value, output and notch per set value) and put the step values on or 0.0002 above what the game stores; (2) pot noise on a band edge: the TCA throttle levers have detents at raw ≈0.31 (idle), ≈0.44 (soft stop), ≈0.724 (CL), ≈0.84 (FLX) and 1.0 (TOGA) (`tools/joyread.ps1` logs the raw axes, X = left, Y = right throttle), so centre a band on each detent and keep band edges 0.02 away. The calibration file has `anti_jitter` 0.008 on the four levers so a lever that has rested for a second does not re-send on noise. Measure, do not guess.
- The app's API-key auto-detect does not see the OneDrive Documents path; the key path is set in the app settings.
- The mod installer deletes `dxgi.dll` in the game's Win64 folder, which is OptiScaler. Keep `dxgi.dll.optiscaler` as backup and restore it after a mod install.
- Word exports of the templates come out as two pages unless trailing paragraphs are dropped; the specs already do that.
- Git identity is set locally in this repo. README uses CRLF line endings.
- `img.png` in the root is a stray screenshot, leave it alone.
